# 百科条目编写规范

版本：1.0 · 更新日期：2026-10-26 · 适用设定：3.0.3

这份规范面向了解赫特维拉设定、但不了解网站代码的作者与 AI。交付物是普通 UTF-8 Markdown 文件；不需要编写 Vue、HTML 页面、数据库记录或搜索索引。网站会从文件生成页面、目录、搜索、反向链接和机器可读数据。

本文说明**当前已经支持的源文件格式**。“必须”是交付要求，“建议”是可以按主题调整的写作方法。格式正确仍需要作者核对事实；程序不会判断人物是否被写偏、事件是否值得单独立条。

## 1. 从零开始的一次交付

1. **确认主题和依据。** 阅读设定中负责定义该主题的原文及必要上下文，确认适用时代、事实状态和名称性质。沿用设定自己的责任边界，不从故事对白推导全局事实。
2. **查询已有对象。** 查找同名、别名及相关事件，决定新增、补充还是合并；复用已有 UID，不为同一个对象再造身份。
3. **选择文件。** 使用[通用条目模板](模板/通用条目.md)、[人物条目模板](模板/人物条目.md)或[独立事件条目模板](模板/独立事件条目.md)。在 GitHub 上查看模板时，使用 Raw 查看或下载原始文件，保留页首资料区。另存为 `content/wiki/条目中文标题.md`，替换全部“待填写”提示。
4. **填写页首资料与正文。** 按下文提供来源、时间、别名和真实链接。初稿使用 `publicationStatus: draft`；完成核对、准备公开收录时改为 `published`。
5. **交付并校验。** 交付完整 `.md` 文件；另列未收录来源、未建立条目或待确认事实。能运行仓库时执行第 10 节的命令；没有执行条件就注明“未运行校验”。

网站作者使用的“责任原文”，是设定包中负责定义某项事实的文件。设定包的 `00_开始阅读.md`、`00_检索/02_责任与边界.md` 与 `02_人物与创作/09_写作规则.md` 提供读取顺序与适用边界；本规范只补充网站的编排和文件格式，不改变设定本身。

### 如何查询已有对象

有仓库时，查阅 `content/wiki/`、`content/stories/`、`sources/reading-map.json` 和对应来源快照。仅有网络读取能力时：

1. GET `https://hetwila.github.io/data/v1/manifest.json`。
2. 跟随清单的 `catalog` 查询文章的 `uid`、`title`、`aliases`、`path`；跟随 `events` 查询独立和段落事件的 `uid`、`articleUid`、`path`。
3. 跟随 `references` 查询来源的 `sourcePath`、网页 `path`、`anchors` 与 `markdownUrl`；必要时通过 `sourceMap` 查找原始锚点已经对应的条目。
4. 从目录中的 `markdownUrl` 或 `jsonUrl` 读取相关全文。这些地址以 `/` 开头时，加上站点域名即可请求；不要固定写死带发布哈希的旧地址。

这些资源通过普通 HTTP 就能读取，无需浏览器截图、OCR 或登录。网站只整理了部分设定：目录里没有某份资料，不表示设定中没有它。未公开草稿的 UID 还需由仓库维护者检查是否冲突。

## 2. 先确定条目如何组织

### 主题与标题

- 标题使用名词或名词短语，例如“禁制”“皇家议政会”“1747年议长选举”。不要把“某地发生了某事”这样的事件表句子直接变成百科标题。
- 一篇条目围绕一个主题解释身份、定义、特征、运作、关系、历史或影响，不沿用原资料的文件编号组织导航。
- 小事件融入相关概念、人物、机构或地点的正文。只有资料能支撑独立背景、过程和影响，且单独阅读有价值的事件，才建立独立条目。需要按年代检索的小事件使用第 8 节的段落事件记录。
- 同名而不同的对象用括号消歧，例如“名称（所属时期）”。别名不能把不同对象混为一项。
- 人物标题使用设定中的完整姓名；常用名、简称、外文名进入 `aliases`。不要自行翻译未确认的名称。

### 人物条目的顺序

人物先回答“她是谁、是怎样的人”，再介绍经历。建议顺序：身份与姓名 → 性格与价值观 → 兴趣与日常 → 重要关系 → 其他有依据的特征 → 按时期展开的生平。外貌、能力等小节按资料与主题需要安排，没有资料的部分省略，不为了凑齐目录补写。

摘要同样以身份和人物特征为主。选举、战争、牺牲等具体事件属于生平的一部分；不能用一次事件定义整个人。现代爱好、职务与生活方式标明适用时代，不投射到童年或前史。资料未给出生日期时，不用外貌年龄或其他人的年龄反推。

### 正文语气与事实

以作者层的客观百科语气说明设定，面向第一次接触该主题的读者解释专名。区分事实、人物看法、时代局限和仍开放的问题；不把世界内传言写成作者已确认的事实。页级 `canon` 也不意味着每句推论都会自动成立。

建议先给简洁定义，再按主题分节。正文里的重要判断应能回到来源；可以重新组织、概括原文，但不增加未经确认的因果、日期、权力、关系或结果。留待确认的问题写入交付说明，必要时在正文明确标注“尚未确定”。

## 3. 一个源文件的结构

文件直接放在 `content/wiki/` 下，**一条目一文件，不建子目录**。当前读取程序只读取这一层的 `.md` 文件。

文件由两部分组成：开头用一对单独成行的 `---` 包住 YAML 资料区（frontmatter），第二处分隔线之后是 Markdown 正文。YAML 使用半角冒号与空格、两空格缩进，不能用 Tab；列表项前用 `- `。建议给字符串加引号，年份和修订号保持数字。

下面是依据现有“禁制”条目写成的完整短示例，展示格式与实际来源。它使用了**已存在的 UID 和标题**，供阅读或在隔离目录中校验，不能作为第二篇“禁制”加入仓库。新条目应另取经过查重的名称与 UID。

```markdown
---
uid: 'wiki:ban'
routeKey: '禁制'
title: '禁制'
description: '通过提高局部平衡的恢复倾向，妨碍外部失衡形成的公共安全基础设施。'
category: '世界与超自然'
entityType: concept
aliases: ['公共禁制', '禁制原理']
nameStatus: descriptive
sourceIds: ['cos-23']
factStatus: canon
narrativeLayer: author-reference
publicationStatus: published
visibility: public
settingVersion: '3.0.3'
revision: 1
worldTime:
  label: '现代社会'
  precision: period
sourceRefs:
  - path: '01_世界原理/04_禁制.md'
    anchor: 'cos-23'
    role: primary
relations: []
events: []
---

## 原理与作用边界

禁制通过提高局部平衡的恢复倾向，使能力者向外界制造的失衡在形成有效现象前迅速回弹。它不会自动抹除个体内部结构，因此异常寿命或某些被动感知未必会被普通禁制消除。

## 历史关联

公共禁制的发展可沿着[年代页](/timeline)继续阅读。
```

将示例保存成源文件时，只取代码块内部内容，不保留外层的三个反引号。正文不再写 `# 禁制`，页面会使用 `title` 生成一级标题；从引导段落或 `##` 二级标题开始。

### 文件名、标题、路径与 UID

| 名称 | 作用 | 例子 |
| --- | --- | --- |
| 文件名 | 仓库里的编辑文件 | `content/wiki/禁制.md` |
| `title` | 人类看到的标题 | `禁制` |
| `routeKey` | 页面地址的标题部分 | `禁制` → `/wiki/禁制` |
| `uid` | 对象永久身份，不是链接地址 | `wiki:ban` |
| `aliases` | 供搜索匹配的别名 | `公共禁制` |

新增条目要求 `title` 与 `routeKey` 一致，文件名严格为 `<routeKey>.md`。标题、文件名、路径保留中文，HTTP 编码交给客户端处理；不能把 `%E7…` 之类编码写进文件名。旧 UID 可以保留原有英文键，新 UID 优先使用中文，不因改名而更换身份。

`routeKey` 必须为 NFC Unicode，长度 1—100（按程序的字符串长度计），首字符是字母、汉字、其他 Unicode 字母、数字或组合标记；不得有首尾空白。后续字符允许字母、组合标记、数字、普通空格及 `_ · （ ） ( ) 、 ， ： 《 》 「 」 -`。不要使用斜杠、反斜杠、`#`、`?`、`%`、句点或半角冒号。`index`、`category` 及其大小写变体为保留名；路径比较时忽略大小写。

UID 前缀：普通条目、人物、机构用 `wiki:`，独立或段落事件用 `event:`。后半部分只允许 Unicode 字母、组合标记、数字、`·`、半角括号和 `-`，**不允许空格、下划线或全角括号**。例如带消歧的标题“名称（限定词）”可用 `wiki:名称(限定词)`。已有 H 事件沿用如 `event:h31-01` 的 UID，原编号仍写作 `H31-01`。没有原编号的对象使用新的中文键，不能编造 H 编号。

文章与段落事件的 UID 必须全局唯一，包括未公开文件；一个事件已经在正文中登记时，不可再给独立文件使用同一 UID。若将它拆成独立条目，移动记录并保留 UID，同时更新所有站内链接。改名、合并时不创建旧地址、重定向或占位跳转页。

## 4. 页首字段逐项说明

以下是当前百科格式的全部字段。标有“可省略”的字段可以不写；显式空列表用 `[]`，不要只留空冒号。初次编写建议保留模板中的全部字段，便于核对。

| 字段 | 必填／默认 | 填写规则 |
| --- | --- | --- |
| `uid` | 必填，字符串 | 经查重的永久身份，遵循上一节的前缀与字符规则。 |
| `routeKey` | 必填，字符串 | 决定文件名和公开路径，与标题一致。 |
| `title` | 必填，非空字符串 | 名词或名词短语；人物为完整姓名。 |
| `description` | 必填，非空字符串 | 建议 1—2 句概括定义、身份或核心特征。用于页面摘要、目录和搜索，使用纯文本。 |
| `category` | 必填，非空字符串 | 一项中文主题分类，见下表；不是列表。 |
| `entityType` | 必填，枚举 | 只能是 `concept`、`person`、`institution`、`event`。 |
| `aliases` | 可省略，默认 `[]` | 字符串列表，写确有依据的别称、简称、外文名；不生成额外页面。 |
| `nameStatus` | 可省略，默认 `descriptive` | `official`：设定确认的正式名称；`working`：暂用名；`descriptive`：为识别对象使用的描述性标题。 |
| `sourceIds` | 可省略，默认 `[]` | 设定原有编号或锚点的字符串列表，供检索；保留原写法，如 `H31-01`、`cos-23`。不代替来源引用。 |
| `factStatus` | 必填，枚举 | 事实确定程度，见下文；一般已确认百科使用 `canon`。 |
| `narrativeLayer` | 必填 | 百科固定为 `author-reference`，表示作者层参考资料。 |
| `publicationStatus` | 必填，枚举 | `draft` 初稿、`review` 待核对、`published` 已公开收录、`withdrawn` 已撤回。 |
| `visibility` | 必填，枚举 | `public` 或 `private`。只有 `published` 且 `public` 才进入网站。 |
| `settingVersion` | 必填，字符串 | 当前必须为 `'3.0.3'`。引用其他版本前需由维护者处理版本支持。 |
| `revision` | 必填，正整数 | 新条目从 `1` 开始，修改已提交条目内容或元数据时递增。不是设定版本或世界年份。 |
| `worldTime` | 必填，对象 | 至少含 `label`、`precision`；规则见第 5 节。 |
| `sourceRefs` | 必填，非空列表 | 每项含原文件 `path`、显式 `anchor`、`role`，见第 6 节。 |
| `relations` | 可省略，默认 `[]` | 有特定意义的有向关系；一般正文链接已经足够，见第 7 节。 |
| `events` | 可省略，默认 `[]` | 本篇正文中的事件索引，见第 8 节。不是相关事件推荐列表。 |

源文件只填写支持的编辑字段。`id`、`path`、`body`、`bodyMarkdown`、`toc`、`markdownUrl`、`jsonUrl`、`backlinks` 等由网站生成，不从导出 JSON 复制到页首资料区。

### 类型与分类

`entityType` 是固定的技术类型；`category` 是目录中的主题名称，两者用途不同。

| `entityType` | 适用对象 | 常用 `category` |
| --- | --- | --- |
| `concept` | 概念、机制、身份、抽象制度；当前地点、地域、文明、物品等主题也使用此类型 | `世界与超自然`、`国家与制度` |
| `person` | 单个人物 | `人物` |
| `institution` | 组织、议事机关、机构 | `国家与制度` |
| `event` | 值得独立立条的事件、战争、变革 | `历史与变革` |

分类是非空字符串，不是固定枚举；优先复用当前分类。确有新的主题群时可以新增如“地理与文明”的分类，网站会生成目录；命名遵循与 `routeKey` 相同的字符约定，避免“人物”“人物介绍”等重复近义分类。当前没有 `place`、`country`、`object` 等 `entityType`，不能自行填入。

### 事实、名称与公开状态

`factStatus` 支持 `canon`（已确认）、`open`（开放问题）、`working`（工作设定）、`deprecated`（已弃用）和 `story-local`（故事局部）。它不等于名称性质，也不等于是否公开：一个描述性标题可以介绍已确认事实，一个 `draft` 文件也可能完全依据 Canon。

百科应以可核对的作者层资料为依据。`story-local` 虽是共享字段支持的值，**不应用来把故事片段装进百科**；故事另有 `/stories` 格式和范围约束。故事中的局部情节只作叙事关联。混合确定程度的资料在正文逐项写明，不编造字段来宣称程序会逐段管理状态。

`private` 与 `draft` 控制网站构建范围，不能隐藏公开 Git 仓库里的文件或提交记录。草稿也需要完整、格式有效的必填字段；不能靠标成草稿绕过 UID、文件名或 YAML 格式错误。

## 5. 世界时间

`worldTime` 当前只支持以下三个字段：

| 字段 | 要求 |
| --- | --- |
| `label` | 必填字符串，人类可读的时代或年份，例如 `'1747年'`、`'现代社会'`、`'生平与人物 · 现状截至2026年'`。 |
| `precision` | 必填，只能是 `year` 或 `period`。 |
| `year` | 可选整数，只有原文允许使用确切纪年时填写；不是字符串、日期对象或公历时间。 |

确切年份用 `precision: year` 并提供 `year`。范围、约数、跨时期主题或日期未定时用 `precision: period`，在 `label` 如实描述，省略 `year`。`year: 0` 是真实的世界纪年0年，未知年份不能填0；“前2953年”在可换算的本世界纪年中写 `year: -2953`。不同原生世界的年代不能自行换算。

独立事件需要数值 `year` 才会出现在当前年代页。没有确切年份的事件仍可在百科正文叙述；不要为了进入年代页捏造日期。当前段落事件索引要求确切年份，不能填时间区间。月日、任期、先后关系可以在正文说明；`start`、`end`、`worldId`、`calendarId`、`birthDate` 等尚不是当前源文件支持的字段。

## 6. 来源引用与来源未收录时的处理

每篇条目至少提供一项来源；建议主定义标为 `primary`，其他支持资料标为 `supporting`。引用应覆盖正文重要事实，人物身份、人格与客观生平可能需要不同责任原文。

```yaml
sourceRefs:
  - path: '01_世界原理/04_禁制.md'
    anchor: 'cos-23'
    role: primary
  - path: '07_历代历史/H31.md'
    anchor: 'h31-01'
    role: supporting
```

- `path` 是设定包内相对 `统合设定/` 的原文件路径，包含 `.md`；不要加 `统合设定/`、`sources/releases/3.0.3/`、`/reference/` 或域名，也不要填网站百科文件路径。
- `anchor` 是原文明确写出的 ID，例如 `<a id="h31-01"></a>` 中的 `h31-01`。不要带 `#`，大小写严格一致。原文只有标题却没有显式 ID 时，不能凭标题猜一个 ID 填在这里。
- `role` 只能是 `primary` 或 `supporting`。同一原文件可以引用多个不同锚点；同一个坐标不重复列出。
- `sourceIds: ['H31-01']` 只是检索编号；`sourceRefs` 才说明编号来自哪个文件、哪个位置，二者不能互相替代。
- 页面自动生成“来源与引用”区域。正文需要就地提示时，可以链接已经存在的来源阅读页，如 `[历史原文](/reference/公共禁制纪元初期（H31）#h31-01)`；这仍不能替代页首 `sourceRefs`。

公开发布前，引用文件必须已进入网站的来源允许列表，并保留原始字节与 SHA-256。核对方法：仓库中查看 `sources/reading-map.json` 与 `sources/releases/3.0.3/manifest.json`，网络读取时查看 `manifest.references` 返回的目录。网页地址取来源目录的 `path`，不要从原文件名推测。

若需要的责任原文尚未收录，作者仍可按原资料的真实路径与锚点编写草稿，并在交付说明中列出所需文件；不要假造锚点、修改来源原文或拿另一份无关来源充数。原文没有显式锚点时，保留问题交维护者处理，不能把该文件标为可直接发布。

维护者公开收录新来源时需要完成三件事：

1. 从已核验的设定包复制原文件到 `sources/releases/3.0.3/<原路径>`，保留原始字节。
2. 将原路径及该文件的真实 SHA-256 加入 `sources/releases/3.0.3/manifest.json` 的 `files`。
3. 在 `sources/reading-map.json` 中追加对象，提供 `path`（原路径）、`routeKey`（唯一中文阅读路径）、`title` 和 `description`，再运行内容准备检查。

作者不必为写条目先学会这套导入流程；交付真实来源坐标、原文件及待导入说明即可。不要编辑 `.generated/`、`public/data/`、`.output/` 来“补上”来源。

## 7. 正文链接与对象关系

### 给读者看的链接

使用标准 Markdown，目标是实际页面的站内路径：

```markdown
[禁制](/wiki/禁制)
[公共系统的启用](/wiki/禁制#h31-01)
[原理与作用边界](/wiki/禁制#原理与作用边界)
[诺菲莉亚](/wiki/诺菲莉亚·薇尔希·伊拉奈德)
[《第一次选择》](/stories/第一次选择)
```

站内链接必须指向已经公开的文章、来源或导航页面；同一批新增文章在一起校验时也可以互链。不要写 `[[禁制]]`、`wiki:ban`、`../wiki/禁制.md` 或编辑器本地文件路径。别名不会自动变成链接，也不会生成别名地址。需要外部链接时使用完整 HTTPS 地址，并自行核对其内容与可访问性；站内链接检查不会验证外部网站。

正文第一次需要理解相关概念时自然地放置链接，不必给每次出现的同一词语都加链接。链接文字可以是常用名，目标仍使用完整的正式路径。尚无页面的概念先保留普通文字，另列为后续条目需求；不要生成死链接或空白占位页。

标题会自动获得锚点，例如 `## 原理与作用边界` 对应 `#原理与作用边界`。包含标点或重复标题时，自动 ID 可能不同，不能凭感觉猜测；可以查看实际页面，或为需要稳定定位的段落使用独立明确锚点。显式 ID 在同页内必须唯一，也不能与标题自动生成的 ID 冲突。

### 写入 `relations` 的关系

普通正文链接会被构建解析成 `mentions` 关系并产生反链，无需再手工列出所有关键词。只有需要明确额外关系时填写：

```yaml
relations:
  - type: concerns
    target: 'wiki:ban'
```

关系从**当前条目指向 `target` 对象**；`target` 填 UID，不能填标题、路径或来源锚点。`concerns` 表示涉及该主题，`mentions` 表示提及，目标须是公开对象。无额外关系时写 `relations: []`。

`depicts` 专用于“故事描写事件”，只能从故事文件指向独立或段落事件。百科不能写 `depicts`，也不用手工建立反向 `depicts`。故事已有指向本条目或其段落事件的关系时，百科的“相关故事”自动生成；百科正文仍可以自然地链接作品。`memberOf`、`parent`、`relatedStories` 等不是当前支持的关系或页首字段。

## 8. 正文里的事件如何参与检索

只需叙述的小事可以直接写在正文。需要被年代页、编号搜索或故事关系单独定位时，在**最合适的一篇所属条目**的 `events` 中增加记录；同一事件不在多篇文章重复登记。其他文章使用普通链接引用该段落。

以下记录来自“禁制”里的既有事件，仅示范格式；不要把它复制进另一篇条目制造重复 UID。把这段 YAML 放在页首资料区，与 `uid`、`sourceRefs` 同级：

```yaml
events:
  - uid: 'event:h31-01'
    title: '南港公共禁制启用'
    description: '0年，瑟芮纳南港首套大型公共禁制系统正式启用，持续覆盖港口、市集及相邻居住街区。'
    anchor: 'h31-01'
    aliases: ['瑟芮纳南港首套大型公共禁制系统正式启用']
    sourceIds: ['H31-01']
    worldTime:
      label: '0年'
      precision: year
      year: 0
    sourceRefs:
      - path: '07_历代历史/H31.md'
        anchor: 'h31-01'
        role: primary
```

在相应正文段落前写出锚点，ID 与记录的 `anchor` 一致：

```markdown
## 公共工程的发展

<span id="h31-01"></span>
0年，瑟芮纳南港首套大型公共禁制系统正式启用，持续覆盖港口、市集及相邻居住街区，运行不再依赖某个能力者一直维持。
```

每条事件记录必须有 `uid`、`title`、`description`、`anchor`、非空 `sourceIds`、非空 `sourceRefs` 和包含整数年份的 `worldTime`；`aliases` 可省略，默认 `[]`。`anchor` 首字符只能是 Unicode 字母或数字，后续还可含 `_`、`-`，不能有空格。它定位的是**本条目的正文**，不是原资料锚点；二者可以相同，也可以不同。

事件索引的 `title` 是年代列表中的事件标签，不会成为百科标题；保留原事件表中的描述也可以。`description` 提供检索摘要，不能取代正文叙述。段落仍按主题自然融入文章，不必每个事件都占一个标题或一张表。

段落事件继承所属文章的公开与事实状态；没有单独的 `publicationStatus`、`visibility`、`factStatus` 或 `routeKey`。不能靠添加这些字段隐藏个别事件；只要所在文章公开，这些事件都会一起导出。独立事件已由自己的 `uid` 与 `worldTime` 进入年代索引，不要再把自身塞进自己的 `events`。

导出中，`articleUid` 表示所属百科，`path` 指向 `/wiki/<routeKey>#<anchor>`，`embedded: true` 表示段落事件；这些字段由网站生成，不写进源文件。事件合并后，其 UID 仍可被故事的 `depicts` 使用。

## 9. Markdown 正文的范围

- 章节从 `##` 开始，需要分层时使用 `###`，保持层级连续。可以在第一个小节前写一段定义；不要重复页面一级标题。
- 使用普通段落、列表、表格、强调、引用和 Markdown 链接。表格适合并列属性或对照，正文负责解释意义。
- 用文字表达核心信息，避免只靠图片、颜色或视觉位置传递事实。不要把正文做成截图。
- 除明确锚点 `<span id="..."></span>` 外，优先使用 Markdown。不要添加 Vue 组件、MDC 容器、JavaScript、CSS、内联样式或组件颜色类。
- 不手工编写页面目录、来源面板、百科导航、反链清单或机器导出；这些由网站生成。需要讲述的实质性关联可以留在正文中。
- 不依赖尚未实现的语法，如 `[[词条]]`、自定义引用标签或新页首字段。新增 `tags`、`summary`、`date`、`cover`、`redirects` 等并不会按想象的方式生效；当前未知字段可能被忽略，不能把未报错当作受支持。

## 10. 交付与校验

### 作者或 AI 交付的内容

交付每个完整源文件及其目标相对路径。正文中不能残留模板提示、“待填写”、省略号占位或交付说明。另附简短说明，列出引用来源、新增／修改对象、未建立的关联对象、未收录的来源及尚待确认的问题；没有相关问题时写“无”。

发布前逐项核对：

- 主题是名词性对象；事件拆分适当；人物介绍先于具体经历。
- 文件名、`title`、`routeKey` 一致；UID 已查重且沿用已有身份；中文名称未被改成英文路径。
- 资料区字段、枚举、缩进、数字与空列表正确；新文件 `revision` 为1，修改旧文件递增。
- 事实、名称性质和时代与责任原文一致；没有把0年当未知、把现代制度搬到古代或把故事对白当事实。
- 所有 `sourceRefs` 有真实原路径和显式锚点；公开发布所需来源已收录。
- 链接目标公开可用，段落锚点存在且唯一；事件登记完整、无重复身份。
- 文章只在准备公开时使用 `published + public`；无模板残留或未解释的未定事项。

### 在仓库中检查

已安装依赖的本地环境，在仓库根目录运行：

```bash
pnpm prepare:content
```

云环境中使用：

```bash
bash scripts/cloud.sh prepare:content
```

这会核对源文件格式、UID 与路径唯一性、公开关系、正文链接、事件锚点、来源哈希与来源锚点，并生成公开集合。它能捕获结构错误，不能代替事实审校。草稿也校验基本格式与身份，但不会进入公开链接和来源核验；改为 `published` 后必须再检查一次。

文章编辑还应在页面预览中核对标题、段落、来源与互链；静态生成和浏览器检查由维护者按 [README](../README.md#检查与构建) 执行。不要让 Nuxt 开发服务、内容监听进程和另一次内容准备／静态构建同时写入生成目录；开发监听已在运行时，先查看它的结果，需要单独运行命令时由维护者停下该任务的服务再执行。

| 提示或现象 | 处理方式 |
| --- | --- |
| `Filename must match routeKey` | 文件名必须是 `<routeKey>.md`。 |
| `Duplicate uid` / `Duplicate route` | 检查独立文章、段落事件和未公开文件，复用或重新分配正确身份，排除路径大小写冲突。 |
| `Missing embedded event anchor` / `Duplicate event anchor` / `Duplicate anchor` | 核对正文显式 ID、事件的 `anchor` 与重复记录。 |
| `Unpublished or missing link` / `Missing anchor` | 修正目标路径或章节；未建立的页面先保留为普通文字。 |
| `Unpublished or missing relation` | `target` 必须是公开对象的 UID，不能是路径或来源编号。 |
| `Missing source anchor` | 核对原路径、显式 ID 和来源允许列表；资料尚未导入时交维护者补齐。 |
| `Source checksum mismatch` / `Source is not allowlisted` | 检查来源导入。不要为了通过检查随意改原文或重算已知基线的哈希。 |
| 条目没有进入页面 | 检查是否为 `published + public`，以及是否放在 `content/wiki/` 顶层。 |
| 事件没有进入年代页 | 独立事件需 `entityType: event` 与确切 `worldTime.year`；段落事件需登记在 `events` 中。 |

### 可直接交给 AI 的任务说明

```text
根据提供的赫特维拉3.0.3责任原文，为指定主题编写百科条目，遵循《百科条目编写规范》。
先查现有目录和事件索引，决定新增、修改还是合并，保留已有UID。
使用当前支持的YAML字段与普通Markdown；标题、文件名和路径保留中文。
人物先介绍身份、性格、日常与关系，再写生平；小事件优先融入所属条目。
不补造事实、来源锚点或H编号，不链接尚未建立的页面。
若无法核对来源或目录，保留草稿状态，在交付说明列明缺项，不声称已通过检查。
输出每个目标路径及完整文件内容，再附来源、待导入资料、未定问题与实际校验结果。
不要改写原始来源快照或手工编辑生成目录。
```
